# 12 Delivery Automation Measurement

資料：`09_PILOT_A_TIMELOG.csv`（Pilot A + Pilot B 建置）。**這是 agent 牆鐘時間；人工時間全部 UNKNOWN。**

## 1. 先講結論：Issue #8 要求的「automation ratio」目前**無法被有意義地計算**
Issue 說「Phase 2 結束後才允許計算 automation ratio」。我嘗試後的結論是：**不允許算一個百分比**，因為：
- 分子需要「被自動化取代的人工時間」，分母需要「人做同一件事的基準時間」。**這輪沒有任何人工時間被量測**（沒有人在迴圈內；客戶訪談、人工審閱、核准時間都沒發生）。
- 能量到的只是「LLM agent 寫出交付物花了多少牆鐘分鐘」，這**不是**顧問真實會花的時間，也不等於人工節省。
- 任何「節省 70%」類的數字在此都會是虛構。

## 4. 可重用 vs 一次性
- **可重用（已具體存在）**：`score.py`、`sensitivity.py`、`processes.csv` 範本、風險登記表結構、eval harness（`run_eval.py`、`cases.py` 格式）、重試/冪等/稽核/遮蔽元件、單元測試骨架、PoC 驗收案例模板。
- **一次性**：情境資料、KB 內容、規則關鍵字（需依客戶重寫）、報告敘述。

## 5. 瓶頸與自動化失敗之處（真實發生）
1. **自動化沒抓到的是我自己的錯**：兩個真缺陷（子字串關鍵字、冪等遺失）都不是 LLM 撰寫時自己發現；一個靠 HELDOUT，另一個靠我**質疑自己測試**。→ 「agent 寫、agent 測」需要獨立的對抗性審查，這是必要的人工/二次審查成本，**不是可忽略的**。
2. 規則詞彙缺口（H11/H12）與改寫型 injection（H24）：決定性規則無法涵蓋語言變化；這正是 LLM 可能有用、同時也最需要評估的地方，但本輪**未測**。
3. DEV 100% 是過擬合訊號，不是品質訊號。

## 6. 第一次執行 vs 第二次執行
- `INFERENCE`（只依「已重複執行的步驟」）：腳本類步驟（評分、敏感度、評估、測試）第二次執行是**秒級重跑**；這是唯一有根據的第二次執行推論。
- **不推估**：敘述類、客戶特定類、人工類步驟的第二次耗時 — 沒有資料。

## 7. 對商業模型的含義
- 可確定：**交付中確定性的部分很多、可模板化且可重跑**（降低邊際成本的合理依據）。
- **不能確定**：人工審閱/簽核/訪談/驗收的時間 — 這才決定有效時薪，而本輪完全沒量。**第一個真實 pilot 的首要量測目標＝人工時間**（見 14 計畫）。
- `Development Readiness Gate` 的「人工工時已量測」條件：**未滿足**（見 17）。
