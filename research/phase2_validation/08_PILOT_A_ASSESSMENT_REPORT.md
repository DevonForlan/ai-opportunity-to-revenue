## 0. 誠實聲明（先看這裡）
1. **選擇偏誤**：我在跑 Pilot A 之前，已先實作 Pilot B（客服 triage）。因此「客服第一名」不是獨立發現。檢驗：對 59,049 種輸入組合（每個流程的月量 ×0.5/1.0/1.5、可自動化比例 ×0.7/1.0/1.3，完整格點）做敏感度分析，P1 仍是 AI 類第一名的比例為 **94.4%**（P5 3.6%、P2 2.1%）。這證明「對輸入擾動穩健」，**不能**證明「現實中客服一定最值得做」，因為輸入結構（客服月量最大）是我設定的。
2. 所有時間為 agent 牆鐘時間；**人工時間未量測（UNKNOWN）**，見 12 號文件。
3. 本評估沒有用任何 LLM 呼叫；所有分析由腳本＋我撰寫的判斷組成。

- **範圍**：5 個流程（客服信件、供應商發票、網站表單進 CRM、每週銷售報表、內部知識問答）。

## 6. Integration Map（假設）
Gmail（唯讀收信/建立草稿）→ 分流服務 → KB → 草稿（待核准）→ 客服人員 → 寄出；工單寫入 CRM（PoC 用 mock）。**PoC 不需要 production credentials**；上線需客戶授權的最小權限帳號（客戶操作）。

## 7. Architecture Recommendation
- **決定性優先**：欄位擷取、PII 遮蔽、規則分類、稽核 — 全為決定性程式。
- **LLM 只用在**規則吃不到的語意分類與草稿潤飾，且**輸出一律需人工核准**；本評估/PoC 未測 LLM 路徑。
- 不用 autonomous agent：流程固定、風險在對客承諾，工作流＋人工核准已足夠。

## 8. Security / Privacy Risk Register
| 風險 | 嚴重度 | 緩解 |
|---|---|---|
| 客戶卡號/身分證/密碼出現在信件 | 高 | 儲存前遮蔽；升級人工；草稿提示勿寄敏感資料 |
| Prompt injection（信件內容操控） | 中–高 | 不讓信件文字成為指令；草稿僅含 KB 文字；人工核准；**模式偵測不完整（見 11）** |
| 草稿做出不當承諾（退款保證） | 高 | 草稿僅 KB 文字；承諾字詞過濾；人工核准 |
| 客戶資料送到第三方模型 | 高 | PoC 不使用；上線前需決策與書面同意；顧問端依公司政策不得餵客戶資料給 Claude |
| 稽核缺漏 | 中 | hash-chain 稽核；設定版本記錄 |

## 9. Prioritization Rationale & Top-1 PoC Spec
**選 P1 客服分流＋草稿（人工核准）**。原因：addressable 工時最大、資料就緒度中等、可在不碰 production 的情況下驗證、風險可由人工核准控制。
**PoC 規格**：輸入 schema、輸出 schema、分類與升級規則、KB 引用、草稿、核准關卡、mock CRM、稽核 — 已實作於 `pilot/phase2/supportdesk/`（見 10 號文件）。

**驗收測試案例（事先約定）**：
1. 正常 16 類（發票/物流/退貨/帳號/產品）→ 產生有 KB 依據的草稿並待核准。
2. 模糊/多重意圖/不明 → 升級，不產生草稿。
3. 缺訂單編號 → 產生澄清草稿並標記。
4. 畸形輸入 → dead-letter，不崩潰。
5. 注入字串 → 升級。
6. 敏感資料 → 不入庫、不外洩、草稿含安全提醒。
7. 重送 → 不重複建單；核准前不寄出。
8. 稽核鏈可驗證。
